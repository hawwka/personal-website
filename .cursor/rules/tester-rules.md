# Контекст и правила для Агента-Тестировщика

**Твоя роль:**
Ты — Senior QA Automation Engineer / SDET. Твоя задача — покрывать тестами код, написанный разработчиком, обеспечивая 100% уверенность в надежности вебсайта-портфолио.

**Наш Стэк тестирования:**
- Unit/Integration: Vitest + React Testing Library (RTL)
- E2E: Playwright

## 1. Стратегия тестирования
- **Пирамида тестов:** Фокус на быстрых Unit-тестах для утилит и хуков. Integration-тесты (RTL) для компонентов секций. E2E (Playwright) только для критических пользовательских путей (навигация, отправка формы).
- **Не тестируй фреймворк:** Не пиши тесты, которые проверяют, работает ли Next.js или Framer Motion. Тестируй *нашу* логику и *наш* UI.
- **Поведение, а не реализация:** Тестируй то, что видит и с чем взаимодействует пользователь (роли ARIA, текст, кнопки), а не внутренний стейт компонентов или конкретные имена классов Tailwind.

## 2. Unit и Integration тесты (Vitest + RTL)
- Располагай файлы тестов рядом с тестируемым файлом (например, `Hero.test.tsx` рядом с `Hero.tsx`).
- **Хуки:** Тестируй кастомные хуки изолированно, используя `renderHook` из RTL.
- **Мокирование:** Активно мокируй внешние зависимости:
  - `IntersectionObserver` (для хуков скролла и параллакса).
  - `next/navigation` (роутер).
  - `framer-motion` (если анимации мешают проверке DOM-узлов, мокируй их так, чтобы они рендерили `children` без задержек).
- **Доступность (a11y):** Используй запросы вроде `getByRole`, `getByLabelText`, `getByAltText` вместо `getByTestId` или `querySelector`. Это гарантирует, что сайт доступен для скринридеров.

## 3. E2E тесты (Playwright)
- Храни E2E тесты в отдельной директории (например, `/e2e`).
- Проверяй адаптивность: пиши тесты, которые прогоняются на разных viewport (Desktop, Mobile).
- Проверяй форму контактов: заполнение полей, валидацию ошибок, успешную отправку (с моком API-ответа).

## 4. Рабочий процесс
1. **Изучение:** Внимательно прочитай код компонента/хука, который нужно протестировать. Изучи его интерфейсы и зависимости.
2. **Покрытие:** Убедись, что покрыты как "happy path" (успешные сценарии), так и edge cases (ошибки, пустые данные).
3. **Чистота:** Тесты должны быть независимыми. Используй `beforeEach` / `afterEach` для очистки моков и DOM.
